# Arity v0.0.1 plan

The wiki in `.wiki/` says what Arity should be. This file says how the first version is built. It is an implementation plan and will go stale; the wiki is the lasting description.

## What v0.0.1 is for

To find out whether Arity's central loop is useful in practice:

1. Someone writes a task for an agent on the board.
2. A model is picked for it without anyone being told which.
3. The result goes back to whoever wrote the task, who rates it from 1 to 5 with a note.
4. Ratings become scores per model.
5. Scores inform the next pick (v0.0.2; in v0.0.1 the pick is uniform).

## Scope

| In | Out, and what stands in for it |
|---|---|
| Conversations with any configured model; the secretary is just a conversation | Project agents: none |
| Delegation by writing a task for an agent, drafted in chat on a task card; the board wakes a worker | A `spawn` tool: none. Work starts from the board, as the wiki describes |
| Blind pick of the worker's model | Harness, skill, MCP and persona trials: the model is the only thing varied |
| Required rating, runs, scores, reveal | The graph database and wiki view: plain tables |
| Results report back to the conversation that wrote the task | Workers handing work on: refused for now |
| A CLI and a Mac app over one core | Phone, sync between machines |
| Models: MLX locally, ChatGPT through its sign-in | Endpoint pool, quotas, Claude and Cursor through their own clients |

## Base

- **Rust core** (`core/`): the journal, the tool loop, model access, the board and the dispatcher. One `Arity` object is its whole surface.
- **CLI** (`cli/`): `arity`, calling the core as Rust.
- **Mac app** (`app/`): SwiftUI, calling the core through bindings UniFFI generates at build time.
- **One data folder** for both: `~/Library/Application Support/Arity` (or `$ARITY_HOME`), holding `arity.sqlite`, `config.json` and the ChatGPT tokens.
- **Models:** `mlx:<id>` through `mlx_vlm.server` on localhost, `codex:<id>` through the ChatGPT subscription.

## Tables

All in `arity.sqlite`.

| Table | One row per | Holds |
|---|---|---|
| `entries` | Journal entry | parent, kind (user, assistant, tool, report, notice), body, model |
| `conversations` | Conversation | name, head entry |
| `tasks` | Task | title, brief, assignee (`people/<user>` or `agent`), created_by (`people/<user>` or `conversations/<name>`), state (open, ready, assigned, in_gates, done), clearance (any, local), priority, due, tags |
| `task_blockers` | Link | task, blocker. Decides ready |
| `trials` | Run of a task | task, conversation, harness, model, started, ended, result, error, lease, reported |
| `ratings` | Rating | trial, score, note, rated_by, rated_at |

## Behaviour

**Task states.** As in the wiki. Ready means no blocker is open, and is recomputed after every board write. A task for an agent is assigned when its run starts, in gates once the run reports, and done when the run is rated: the rating is the one gate until gates are written. Run status (running, failing, needs rating, rated) is the latest run's, shown next to the task.

**Drafting.** A task is drafted on a card bound to a conversation. The card is `draft` entries in the conversation's chain, so it survives restarts and forks. A model fills or changes it with `propose_task`; the person edits fields directly, and those edits reach the model as a user message. While a card is open it sits where the composer was, with a one-line message field above it, and the model's system prompt shows it. Add puts it on the board, written by the conversation; Dismiss closes it. New Task opens a conversation with an empty card.

**Delegating.** Assignee `agent`, on the card, through `add_task`, or by changing it with `update_task` before work starts. The tool tells the writer the result will come back later, so it finishes its turn instead of waiting. A conversation can also do a task itself in its reply and mark it done.

**Dispatching.** `work_once` delivers one finished result or runs the most pressing ready task for an agent (priority, then due date, then age). The app calls it in a loop while open, and so does `arity work`. A claim is a lease on the trial row, taken in a write transaction, so two dispatchers never run the same task. A run whose dispatcher died is resumed from the journal once its lease runs out. A failed run is retried a minute later.

**The blind pick.** Uniform among the `workers` listed in `config.json` that the task's clearance allows: `local` allows only `mlx:` workers.

**Workers.** Each run has its own conversation, `task-<id>` (`task-<id>-<n>` for a rerun), with a worker prompt and read-only board tools. Its last answer is the result.

**Reporting.** A finished result is appended to the writing conversation as a report, and that conversation is woken with the model it last used. A task written by a person (`people/<user>`) waits on the board for their rating.

**Hiding the model.** The report carries only the result. A run's model is hidden in its conversation, in `runs`, and as a default model until the run is rated. Scores count rated runs only, so unrated runs cannot be traced to a model. `reveal` shows it on request.

**The rating gate.** A conversation that ends its turn with a reported, unrated result gets a notice asking it to rate, up to three times since the last report. Then it is let through, and the run stays unrated for the user.

## Commands

| CLI | App | Does |
|---|---|---|
| `arity chat`, `resume`, `log`, `ls`, `fork` | Chat window, sidebar, Fork From Here | Talk to a model |
| `arity draft <conv> --new`, `arity chat` | New Task (⌘T) | Open a card and draft it with a model |
| `arity draft <conv> [fields]` | Edit the card | Change the draft |
| `arity draft <conv> --add` / `--dismiss` | Add to Board (⌘↩) / Dismiss | Put it on the board, or close it |
| `arity task "…" [fields]` | | Write a task directly |
| `arity edit <task> [fields]` | Click a task on the board | Change a task; `--agent` / For: An agent hands it off |
| `arity board`, `done` | Board | See and tick off tasks |
| `arity work` | Runs while the app is open | Run waiting tasks, deliver results |
| `arity runs` | Runs in the sidebar | Runs, model hidden until rated |
| `arity rate <run> <1-5> <note>` | Stars on a finished task | Rate as the user |
| `arity scores` | Scores on the board | Average rating per model |
| `arity reveal <run>` | Shown after rating | Which model did a run |

## What is built

The journal with crash-safe resume and fork; MLX and ChatGPT; both front ends; the wiki's task fields and states, with blockers deciding ready; task cards drafted in chat; delegation, the blind pick with clearance, workers, reports, rating by model and by user, masking, scores, reveal; the rating gate. Unit tests cover the rating gate, blockers deciding ready, migrating the first board, and a card's life.

## What is left

1. **Interrupting.** Stop a running turn; send while one is running (steer or follow-up).
2. **Talking to a worker directly** after its run, without breaking blindness before it is rated.
3. **Papercuts.** A tool and a button to file one.
4. **Tests on a scripted model** for the full loop, kill and resume included, and a check that no model name reaches the writer.
5. **One writer per conversation.** A report can wake a conversation while the user is sending in it; two loops on one conversation would interleave.
6. **Requirements and gates** on tasks, once their lists are written.
7. **A real session** with two or three models, long enough to see scores separate.

## Done means

- A chat where the secretary delegates, the result comes back, and it rates it.
- Scores show per-model averages after a few dozen runs.
- No model name appears before a rating, except through `reveal`.
- Killing the process mid-run and restarting loses nothing.
- The scripted end-to-end test passes.

## Risks

- **Small local models may call tools poorly.** The writer can be a stronger model than the workers; only worker picks are blind.
- **Raters may rate everything 5.** The first runs were all 5/5. If that holds, ratings carry no signal, which is the stage's question.
- **Cost is zero for local models,** so scores rest on ratings and time until paid API models are added.
