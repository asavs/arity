# Arity v0.0.1 plan

The wiki in `.wiki/` says what Arity should be. This file says how to build the first version. It is an implementation plan and will go stale; the wiki is the lasting description.

## What v0.0.1 is for

To find out whether Arity's central loop is useful in practice:

1. The secretary hands a piece of work to a subagent.
2. The subagent's model is picked without anyone being told which.
3. The secretary rates the result from 1 to 5 with a paragraph.
4. Ratings become scores per model.
5. Scores inform the next pick.

Everything else in the wiki widens this loop. None of it is needed to close it once.

## Scope

| In | Out, and what stands in for it |
|---|---|
| Secretary: one long-lived conversation | Project agents: none |
| Subagents, fresh or forked | Task board and waking by fit: the secretary spawns directly |
| Blind pick of the model | Harness, skill, MCP and persona trials: model is the only thing varied |
| Required rating, trials table, scores, reveal | The graph database and wiki view: three plain tables |
| Steer, follow-up, and stop-then-send | Endpoint pool, quotas, subscriptions: a config file listing models |
| Talking to a subagent directly | Computer pool and workspaces: one local folder per conversation |
| Roles as markdown files | Vault, access broker, clearance: agents get no credentials |
| Papercuts collected | Papercut fix loop, agents rating users |
| Command line only | Any other interface |

The harness is recorded on every trial as `pi`, so later versions can add harnesses without reworking old data.

## Base

- **pi-durable 1.5.2**, pinned exactly, with `pi-ai`, `chord` and `pi-schema` at the same version. Storage is its SQLite backend, which uses Node's built-in SQLite.
- **Node 22.19 or newer.** Not currently installed on this Mac's PATH.
- **Models:** local models served by MLX over an OpenAI-style endpoint, plus any API keys that are set. MLX is not currently installed.

The spikes on the branches `spike/pi-durable` and `spike/connectome` are the evidence for this choice. All their results came from a scripted stand-in model.

## Layout

```
arity/
  package.json            pinned dependencies
  arity.config.json       models available, default role, limits
  roles/*.md              one file per role: system prompt and tool list
  src/
    harness.ts            the only file that imports pi-durable
    router.ts             pick a model for a spawn
    store.ts              our three tables
    secretary.ts          the secretary conversation and its tools
    tools/spawn.ts        create a subagent, fresh or forked
    tools/rate.ts         record a rating
    tools/papercut.ts     record a papercut
    cli.ts                chat, runs, attach, scores, reveal
  test/                   end-to-end runs on the scripted model
```

**`harness.ts` is the seam.** It exposes a small set of operations: open, start a conversation, send (steer or follow-up), stop, fork, read the answer, read usage. Nothing else in the code touches pi-durable. This contains its "API changes without notice" risk, and it is where another harness would plug in later.

## Tables

| Table | One row per | Columns |
|---|---|---|
| `trials` | Subagent run | id, parent conversation, child conversation, role, harness, provider, model, task, fresh or fork, started, ended, tokens in, tokens out, cost |
| `ratings` | Rating | trial id, score, paragraph, rated at, rated by |
| `papercuts` | Papercut | id, conversation, role, text, filed at |

They live in the same SQLite file as pi-durable's own tables. Writes are made safe to repeat, because they happen outside pi-durable's own save step.

## Behaviour

**Pick.** Uniform random among the models the config allows for the role. A smarter policy waits until there is data to be smart about.

**Hiding the model.** Three rules, all confirmed in the spike:

- The parent receives only the child's answer text and an opaque result id.
- Nothing about the child goes in the tool result's side fields.
- The parent is never given the child's raw messages or a fork of the child.

The command line shows model names only through `reveal`.

**Rating.** A `rate` tool, plus a hook that blocks the secretary's final answer while any result is unrated. After three push-backs the trial is marked unrated and the secretary is let through, so a model that refuses cannot loop forever.

**Interrupting.** Steer and follow-up are pi-durable's own. Pressing Esc in the chat stops the turn; the next message is then sent normally.

**Nesting.** A subagent may spawn its own subagents and must rate them, by the same mechanism. Depth is capped at 2 below the secretary.

## Commands

| Command | Does |
|---|---|
| `arity chat` | Talk to the secretary |
| `arity runs` | List subagent runs, without model names |
| `arity attach <run>` | Talk to a subagent directly |
| `arity scores` | Average rating, run count, tokens and cost per model |
| `arity reveal <run>` | Show which model did a run |

## Build order

Each step ends with something that can be run.

1. **Environment.** Install Node. Scaffold `arity/` with pinned dependencies.
2. **Harness layer.** A conversation saved to SQLite that resumes after the process is killed.
3. **A real model.** Confirm pi-ai can use an MLX endpoint. This is unverified and is the first real risk. Fall back to an API key if it cannot.
4. **Secretary and chat.** Including steer, follow-up and stop.
5. **Roles and spawn.** Fresh and fork, with the model picked and hidden.
6. **Rating gate and tables.**
7. **Runs, scores, reveal, attach.**
8. **Papercut tool.**
9. **End-to-end test** on the scripted model, covering spawn, rate, score, kill and resume, and a check that no model name reaches the parent.
10. **A real session** with two or three local models, long enough to see scores separate.

## Done means

- A chat where the secretary delegates, the result comes back, and it rates it.
- `arity scores` shows per-model averages after a few dozen runs.
- `arity reveal` works, and no model name appears anywhere else.
- Killing the process mid-run and restarting loses nothing.
- The end-to-end test passes.

## Risks

- **pi-durable is experimental.** Pinned, and behind `harness.ts`.
- **Nothing has run on a real model yet.** Step 3 exists to find out early.
- **Small local models may be poor at calling tools.** If the secretary cannot reliably call `spawn` and `rate`, the secretary needs a stronger model than the subagents do. That is allowed: only subagent picks are blind.
- **Cost is zero for local models,** so scores will rest on ratings, tokens and time until paid models are added.

## Needed from the user

- Node and MLX installed, or a decision to use API keys instead.
- Which two or three models to start with.
- TypeScript or plain JavaScript. The plan assumes TypeScript.
