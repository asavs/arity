  description below is of the program as it actually runs. Here is the

  The flow of information

  The whole program is one queue and one switch. Everything else either fills
  the queue or remembers what came off it.

  Two kinds of data, one crossing. A Spec is seven strings: seat, model, role,
  skills, tools, harness, effort. None of them is text, every one is a key into
  a file. A State is the same thing after lookup: the role file's text, each
  skill's text, each tool's JSON schema, the bot's last ledger entries, all
  copied in. The function that does the copying is cast.resolve, and it runs
  once, at birth. After it, nothing in the program opens the library or the
  ledger again until the next birth. That is the rule the README states, and it
  is literally true in the code.

  One turn, hop by hop. Trace arity "hi":

  1. The front door wakes reception. Wake means: take the bot's lock file, ask
     cast for a State, write a birth line to a new session file. The State goes
     into a dictionary keyed by bot name and stays there until retirement.
  2. The front door builds a Message(sender="asa", text="hi") and hands the
     State and that event to Loop.run.
  3. The loop puts the event on a queue. Then it loops: pop an event, append it
     to the session file, call transition, get back the same State plus a list
     of effects.
  4. transition is a pure function with four cases, one per event type. For a
     Message it appends a user line to the conversation, remembers the sender,
     and returns one effect: CallModel, which is just the system text joined,
     the tool schemas, and the message list. That triple is everything the model
     will ever see.
  5. The loop's switch has three arms. CallModel goes to the Model seam. The
     wire formats it for the provider, posts it, subtracts from the seat's
     quota, and turns the reply into a ModelCompleted event. The loop pushes
     that event on the queue. A network failure becomes a ModelFailed event
     instead. Nothing is swallowed.
  6. Back to step 3. transition sees ModelCompleted with no tool calls, appends
     the assistant line, and returns a Send with no call id. That means "this is
     my answer to whoever asked."
  7. The loop's third arm, Send, is the post office. The recipient is a person,
     so it goes out the Transport seam, which is a print statement. The queue is
     empty, run returns.

  The recursion that makes bots a team. If in step 6 the model called the
  message tool instead, the moment turns that tool call into a Send with a call
  id. The post office sees a bot name and does something that is worth staring
  at for a minute: it wakes that bot and calls Loop.run on it, right there,
  inside the current run. The engineer's whole turn happens as a nested function
  call. When it returns, the engineer's final output is wrapped as a
  ToolCompleted and pushed on reception's queue, so from reception's model's
  point of view the message tool just returned a string. There is no scheduler,
  no mailbox, no threads. A bot-to-bot message is a Python call stack. That is
  also why the 1.0.1 notes list "a bot messaged mid-turn" as a defect: the stack
  cannot express two bots talking at the same time.

  Two memories, one derived table. The session file is a journal of every event,
  verbatim, written before the moment sees it. So the State is always a fold
  over that file, and resume is exactly that fold followed by redoing the last
  event. You saw the demo print the engineer's answer twice; that is the redo,
  on purpose. The ledger is the other memory: per bot, prose, written at death
  by two model calls and read at birth into the system text. The store remembers
  what happened, the ledger remembers what it meant. The scorecard is not a
  store at all. store.rows turns every session file into one dict, standings
  counts wins per value of one field, and cast.choose reads that ranking before
  asking the seat table who has quota. That is the closed loop: store to
  scorecard to cast to state to store.

  A trial is a deep copy. trial.fork re-resolves a State from a different Spec,
  copies the conversation in, and gives it its own session file whose birth line
  points at the parent. Feed all N the same event, print outputs, the human
  types a number, the number becomes an outcome line in each fork's file.
  Nothing about the kernel knows a trial exists.

  Two things I noticed that the docs don't say. ToolSeam.schemas() is never
  called anywhere; the tool block the model sees comes from the library at cast
  time, not from the seam. And loop.live is keyed by bot name, so there can
  never be two live kernels for one bot, which is the thing the long-lived-forks
  item runs into.

  The TODO items, simplest versions

  I've ordered these by how much of the flow each one touches, because that is
  what teaches the system. Line counts are rough.

  1. message(to, content, kind). Do this first. It is the smallest change and it
     touches every hop. Add an optional kind string to the message tool's
     schema so the model can fill it. Add kind: str = "" to both the Message
     event and the Send effect. In the moment, copy it from the tool arguments
     into the Send. In the post office, copy it from the Send into the Message
     it wakes the recipient with. The store journals it for free, because it
     serialises events with asdict. In rows, read it off the first Message into
     the row. Then standings(role, "kind") already works, because that function
     falls back to row fields. About eight lines across five files, and you will
     have followed one string from the model's mouth to the scorecard.
  2. The judge. A function that takes the forks' outputs, builds one prompt
     saying "here are N answers to this task, reply with the number of the
     best", sends it down any existing wire, and parses the integer. Return that
     as pick. In the front door, call it when the person presses enter without
     choosing. About fifteen lines, and the loop closes without a human for the
     first time. The hidden-tests variant needs a task bank that doesn't exist
     yet, so leave it.
  3. The fan-out plug. A class with execute and schemas, holding two inner tool
     seams and a judge function. execute runs the effect against both and
     returns whichever the judge picks. Plug it in through Loop(tools_for=...).
     The moment never knows, which is the whole lesson of the seams file. The
     one design wrinkle: to record which runner won, the plug needs the session
     id, and a seam only sees the effect. Simplest fix is to hand the session id
     to the plug when you build it. For the outcome line, write a record with
     the factor as a field, and have rows merge any extra outcome fields into
     the row. Then standings(role, "mcp") works with no further change, the same
     way worked does today.
  4. Long-lived forks. Keep this out of the kernel entirely. In the front door,
     let the thing you are talking to be a list of States instead of one. After
     a trial with no pick, keep the forks in that list, send every later line to
     all of them, and print side by side each turn. A pick collapses the list
     back to one, exactly as today. About twenty lines in one file. It gets you
     trajectories without touching the loop or the moment.
  5. The sandbox. A second Tools plug. Instead of importing the runner and
     calling it in process, run it as a subprocess in a temp folder with the
     arguments passed as JSON. About twenty lines. Same shape as the fan-out, so
     once you have written one plug the second is a copy.
  6. Real MCP. This is the one where the naive version is not that naive. MCP is
     JSON-RPC over a subprocess's stdin and stdout, and the Tools seam maps
     onto it cleanly: tools/list is schemas, tools/call is execute. But because
     the model's tool block comes from the library at cast time and not from the
     seam, you either dump the server's tool list into library JSON files by
     hand, or teach cast to ask the seam. I'd do the first. Sixty lines or so
     with only the standard library. Do it after the fan-out exists, so there is
     somewhere for it to plug in.
  7. Cache breakpoints is one line in the Anthropic wire, but the checklist is
     right that the research comes first. That research is blocked on the 1.0.1
     defect about cached-token counts, which is itself about ten lines in the
     store.

  I'd leave OAuth and the TUI where the TODO leaves them.

  The first three items form a nice sequence: item 1 makes you follow a value
  through every seam, item 2 closes the evaluation loop, item 3 makes you write
  your first plug. After those, you will know the program the way its author
  does.

● Yes. Grounded in what's actually in the files, here are the ones I'd add,
  split into dumb engineering and the more creative ones.

  Dumb engineering, each under twenty lines

  - A loud Observer. The Observer seam exists and the only plug is Quiet. A plug
    that prints one line per event and per effect gives you a live trace of the
    whole flow for free. It is also the best teaching tool for item 1 on the
    last list.
  - arity show <session>. The archivist's transcript renderer already exists in
    the ledger file. Point a subcommand at it and you can read any session as
    prose instead of JSONL.
  - arity standings <role>. The scorecard has the function. Nothing prints it.
    Same for rows.
  - Fold every journal as a test. Loop over every session file, fold it, assert
    nothing raises. That is a regression test for the moment that grows itself
    every time you use the program.
  - Seats reset on their clock. When resets_at is in the past, set remaining
    back to one. Five lines in the seat table, and it is already listed as a
    1.0.1 defect with no policy. This is the policy.
  - Epoch from a hash. Replace the hand-bumped library/EPOCH with a hash of the
    role, skill and tool texts. Old evidence stops voting the moment a file
    changes, and nobody has to remember to bump anything.
  - Dollars per row. A price table per model id, multiplied into rows.
    Cost-aware ranking then needs no new data.
  - arity doctor. Which key env vars are set, which seats are reachable, which
    lock files are stale. Half the future debugging sessions end here.
  - A retrying plug. A Model seam plug that wraps another Model seam and retries
    on a 429. Its cousin is a fallback plug: try seat A, on failure try seat B.
    Both teach that plugs compose, which the seams file says but nothing
    demonstrates.

  Creative, but still small

  - Replay a session as someone else. The journal holds every Message the person
    sent. Feed only those, in order, to a fork on a different spec and let it
    regenerate the rest. You get a counterfactual for any past conversation.
    Every old session becomes a benchmark, and the judge from the last list
    scores it.
  - The person is a Model plug. Put yourself in the staff list with a harness
    called human. The plug behind it reads stdin and returns a ModelCompleted. A
    Send to a person is then just a wake, the Transport seam disappears, and
    the phone from the axioms is a plug. This is the mid-turn question answered
    by making the human a bot.
  - An inbox folder as the transport. For when the person is not at the
    keyboard. A Send to a person writes a file, the person answers by writing a
    file back. The same folder is the mailbox answer to the mid-turn defect and
    to two arity processes on one home.
  - A note tool. Lets a bot append to its own ledger mid-life instead of only at
    death. Pair it with a recall tool that reads further back than the five
    entries cast wakes with. That is the deferred memory tier, done as two
    library tools and no kernel change.
  - Report versus archive as data. Every retirement writes two accounts of the
    same session. A model reading both and scoring the gap gives you an honesty
    axis per bot per spec. The old repo did this and it is one more field on the
    row.
  - A task bank folder. One markdown prompt plus one check script per task.
    arity bench runs each through N specs and the check script is the pick. This
    is what makes the judge item real, and it is the closed loop the checklist
    calls "the part that is ours."

  One I'd resist

  The pull toward threads. The nested-call post office is the thing that makes
  the program readable as a stack. Every item above can be done without a
  scheduler. The inbox folder handles the one case that looks like it needs
  concurrency.

  If I had to pick three from this list to go with the earlier three: the loud
  Observer first, then replay-as-someone-else, then the task bank. Together they
  turn the store from a crash log into a dataset.

    reception  <- ToolCompleted  message: 0 errors
    reception  -> CallModel      1 tools, 965 chars of system, 3 messages

● Two answers. First the mentality, then the code that fits in a 1.0.n session.

  Changes to mentality

  - Journal it or it didn't happen. This is already the rule, but the article
    shows how it fails: not by someone breaking it, but by someone adding a
    feature with its own little state. Todo lists, retry counters, a subagent
    registry. The new habit is a question asked of every change: is this a fold?
    If a value can't be rebuilt from the session file, it either goes into the
    file or it is explicitly disposable, like last_call_at. Write which in the
    docstring.
  - Audit, don't wait. He found 15 of 17 stateful extensions broken by sitting
    down and trying rewind and resume on each. You can do the same to arity in
    an hour: list every place state lives, try resume against each, write the
    table. You already know three entries: the trial winner, loop.live, seat
    quota.
  - Every tool definition taxes every turn. His numbers make this concrete. The
    roster is a budget, and a skill that names three tools is spending it. Keep
    the fan-out invisible to the model, and treat a schema change as a cold
    start in the cost column.
  - Intent before result. Every call says what it is for, in the caller's words,
    before it runs. It costs the model a few tokens and makes the journal
    readable without the tool output.
  - Limits belong to the seam, not the tool. Truncation and time bounds go in
    one place, the plug behind the Tools seam. No runner should know about them.
  - Cancellation needs a process boundary. Cooperative cancellation fails when
    work forgets to check. That settles the sandbox design: it is a subprocess
    with a timeout, not an in-process call with a flag. The current LocalTools
    cannot be interrupted and that is fine only because nothing has hung yet.
  - The four modes are a thought experiment, not a build target. For each
    change, ask which of his four modes would break it, and write the answer
    down. Do not build for the mode. That is the whole difference between arity
    and omp², and it should stay a choice rather than an oversight.
