# Arity v0.0.1 plan

The wiki in `.wiki/` says what Arity should be. This file says how the first version is built. It is an implementation plan and will go stale; the wiki is the lasting description.

## What v0.0.1 is for

To find out whether Arity's central loop is useful in practice:

1. Someone writes a task for an agent on the board.
2. A model is picked for it without anyone being told which.
3. The result waits for whoever the task belongs to, who rates it from 1 to 5 with a note. For a task filed in a chat that is the user.
4. Ratings become scores per model.
5. Scores inform the next pick (v0.0.2; in v0.0.1 the pick is uniform).

## Scope

| In | Out, and what stands in for it |
|---|---|
| Threads: a conversation that may have a task attached. A chat is a thread with no task, a run is the thread of a task an agent is doing; the secretary is just a chat | Project agents: none |
| Delegation by writing a task for an agent, drafted in chat on a task card; the board wakes a worker | A `spawn` tool: none. Work starts from the board, as the wiki describes |
| Blind pick of the worker's model | Harness, skill, MCP and persona trials: the model is the only thing varied |
| Rating by the user, never required; runs, scores, reveal | The graph database and wiki view: plain tables |
| A note of the result in the chat the task was filed in | Workers handing work on: refused for now. The rating gate and rating by a model are kept, tested, for when they can |
| A CLI and a Mac app over one core | Phone, sync between machines |
| Models: any OpenAI-compatible endpoint in `config.json` (MLX, Nous Portal, OpenCode Zen, any API key), ChatGPT through OpenAI's sign-in for apps | Endpoint pool, quotas, Claude and Cursor through their own clients |

## Base

- **Rust core** (`core/`): the journal, the tool loop, model access, the board and the dispatcher. One `Arity` object is its whole surface.
- **CLI** (`cli/`): `arity`, calling the core as Rust.
- **Mac app** (`app/`): SwiftUI, calling the core through bindings UniFFI generates at build time.
- **One data folder** for both: `~/Library/Application Support/Arity` (or `$ARITY_HOME`), holding `arity.sqlite`, `config.json`, `keys.json` (API keys, mode 0600), `models-cache.json`, `usage.json`, `checks.json` (the last result of each key check) and the ChatGPT sign-in (`codex-auth.json`, mode 0600).
- **Models:** `<provider>:<id>`, where a provider is a name, an OpenAI-compatible base URL and, if it needs one, a key; or `codex:<id>` through the ChatGPT subscription.

## Providers

`config.json` names them under `providers`, each with a `url`, `key: true` if it needs an API key (or the name of another provider whose key it shares), `session_header` if it wants a stable id per conversation, and optionally `models` to offer when it has no `/models` list. These are there unless the file overrides them, field by field:

| Provider | URL | Key |
|---|---|---|
| `mlx` | `http://127.0.0.1:8080/v1` (`mlx_vlm.server`) | none |
| `openai` | `https://api.openai.com/v1` | an OpenAI API key |
| `nous` | `https://inference-api.nousresearch.com/v1` | an API key made at portal.nousresearch.com |
| `opencode` | `https://opencode.ai/inference/openai/v1` (OpenCode Zen, now called Console) | an API key made at opencode.ai; pay per request |
| `opencode-go` | `https://opencode.ai/inference/go/openai/v1` (the OpenCode Go subscription) | the same key as `opencode` |

Nous Portal is only a preconfigured provider. Its [OpenAPI spec](https://portal.nousresearch.com/api/openapi) documents bearer API keys from the portal ("activate a subscription, then generate an API key"). The OAuth sign-in Hermes Agent uses is not open to other clients: its client id and redirect URIs are bound to Hermes's own gateway ([Hermes docs](https://hermes-agent.nousresearch.com/docs/guides/desktop-native-signin)).

Keys live only in `keys.json`. A provider that needs a key and has none is left out of the model list, and a model on it is refused before any call. An error that would contain a key has it cut out. A saved key is checked without running a model: the provider's `/models` with the key, then a request for a reply to no messages. A bad key is refused (401 or 403) and a good one gets a complaint about the empty request. The models sheet shows the result, and `arity key check` prints it. Model lists come from each usable provider's `/models`, cached for a day. ChatGPT's list comes from its own `/models` while signed in.

OpenCode Zen's docs say every text model also works through chat completions, which it translates, so it needs nothing of its own. Its free models are only for OpenCode itself and will fail here. [OpenCode Go](https://opencode.ai/v2/docs/console/go/) admits other agents that name themselves and send a session id per conversation: every request carries the user agent `Arity/<version>`, and `opencode-go` sends `x-opencode-session`, a hash of the conversation's name.

Nous Portal lists its models at `/models` and takes tool calls, though its spec documents neither. Paid models there need credits; the `:free` ones answer on a subscription key.

## Accounts and plans

Both front ends show accounts, not endpoints. An account holds at most one key, and each of its plans is one way of reaching its models, with its own status:

| Account | Plans |
|---|---|
| OpenAI | ChatGPT (the sign-in), API (key) |
| OpenCode | Zen (key, pay per request), Go (the same key, a subscription) |
| Nous Portal | Inference (key) |
| This Mac | MLX |

A provider's `account`, `account_title`, `title`, `note` and `page` in `config.json` place it; one the user adds is an account of its own. Each plan with a key shows whether it works, or the provider's reason for refusing; a plan on a borrowed key that is refused links to subscribing.

Every plan has the same parts: how it is reached (nothing, the account's key, or a sign-in), its status, where to subscribe, and its usage. Every OpenAI-compatible provider is reached through one `Endpoint` (`core/src/endpoint.rs`), which holds its URL, key, extra headers and whether it reports usage; chatting, listing models and checking the key all go through it.

Usage is one of: nothing to count (this Mac), not reported by the provider, nothing yet, or limits with what is left and when each is full again. A provider marked `"usage": "headers"` (Nous, the OpenAI API) reports `x-ratelimit-*` headers on its replies; the latest are kept in `usage.json` and aged as their reset times pass. The sheet shows the two limits closest to running out as bars of what is used (green, orange under 30% left, red under 10%), the numbers and reset times on hover, and says so when a provider does not report usage. OpenCode Go has a usage endpoint that answers only with a subscription, so it is not read yet; nothing was found for Zen or ChatGPT.

## Choosing a model for a chat

A chat does not ask for a model. Beside the composer are four choices, Smart, Fast, Free and Private, and Arity picks the model (`pick` in `core/src/lib.rs`, the ranking in `core/src/leaderboard.rs`):

| Choice | Candidates | Ranked by |
|---|---|---|
| Smart | every model you can reach | quality |
| Fast | every model you can reach | wait for a typical reply: time to first token plus 300 tokens at the output speed |
| Free | local models, and subscription plans with quota left; never a pay-per-token key | quality |
| Private | local models only | quality |

Reachable means offered by a usable provider (a key saved, or the ChatGPT sign-in), less local servers that do not answer within 0.8 s and providers whose key was refused at its last check. Local is a provider on localhost. A subscription is `codex`, a provider marked `"billing": "subscription"` (OpenCode Go), or a model ending in the provider's `free_suffix` (Nous's `:free`); it has quota left unless its reported limits show one at zero, and a plan that reports nothing counts as having some. Everything else with a key is pay per token.

Ties in quality go to the quicker model, and where no candidate has a quality figure speed decides. A model with no figures ranks last. The pick says why in a few words ("best of 3 local models"); a choice with no candidates fails saying what is missing ("No local model is running…").

The choice is remembered between launches. A chat's model is picked when its first message is sent and kept for the chat; changing the choice picks again from the next message. Other… names a model from a searchable list. The window's subtitle shows the model that answered and why. `arity chat <conv> --smart|--fast|--free|--private <message>` picks the same way.

**The leaderboard.** Per model, a quality figure (0–100) and two speeds, from two sources kept apart:

- Public: `core/data/leaderboard.json`, a hand-gathered stopgap checked in with the source of every figure, for about twenty models across the default providers and common local ones. Quality is the Artificial Analysis Intelligence Index; hosted speeds are Artificial Analysis's (its time to first token includes reasoning), local ones community MLX runs. Gaps are left empty. It matches a model by its id without provider or organisation, or by one of its `aliases`. A proper leaderboard source replaces the file, or `leaderboard::public`, without touching the pick.
- Arity's own: the average rating of a model's rated runs, and the time to first token and output speed of every streamed chat reply, in the `speeds` table. Output speed is estimated at four characters a token; replies with no text or too short to time give no speed. Runs are not timed, since a speed would hint at an unrated run's model.

Each speed the pick uses is a weighted average: the public figure counts as five observations and each own measurement as one, so public figures are the starting value and Arity's take over as they accumulate. Ratings do not stand in for quality, since stars on easy tasks would outgrow every benchmark; they shift it, 10 points for each star a model's average is above or below the average over all rated runs, scaled by n / (n + 5) for n rated runs. A model with no public figure starts at the average public figure of the models it is picked among, so one good rating moves it a point or two. Where only one of a model's speeds is known, the other counts as typical (1 s, 50 tokens a second). `arity leaderboard` prints the table with the source of each figure.

## ChatGPT

Signed in the way OpenAI documents for [open-source and locally hosted apps](https://developers.openai.com/siwc/token-sharing-open-source). The first sign-in registers Arity under a host id kept in the data folder, and OpenAI issues a client id owned by the user. Tokens are for the public Responses API (`api.openai.com/v1/responses`) and draw on the plan's usage: Plus shares a five-hour limit across apps, Pro has none. Refreshes take a lock, since refresh tokens rotate and the app and CLI share them. A sign-in from the older Codex CLI client is treated as signed out.

## Tables

All in `arity.sqlite`.

| Table | One row per | Holds |
|---|---|---|
| `entries` | Journal entry | parent, kind (user, assistant, tool, report, notice), body, model |
| `conversations` | Conversation | name, head entry |
| `tasks` | Task | title, brief, assignee (`people/<user>` or `agent`), created_by (`people/<user>`, or `conversations/<name>` for an agent's run), origin (the conversation it was filed in), state (open, ready, assigned, in_gates, done), clearance (any, local), priority, due, tags |
| `task_blockers` | Link | task, blocker. Decides ready |
| `trials` | Run of a task | task, conversation, harness, model, started, ended, result, error, lease, reported, abandoned |
| `turns` | Conversation a turn is running in | owner, model, lease, the reply's text so far, stop flag. Cleared when the turn ends |
| `queued` | Message sent while a turn runs | conversation, text. Moved into the journal between replies |
| `ratings` | Rating | trial, score, note, rated_by, rater_model (empty for a person), rated_at |
| `speeds` | Timed chat reply | model, time to first token, output tokens per second, when |

## Behaviour

**Turns.** A turn runs the model until it answers without calling a tool. Each step is decided purely from the journal, which records only finished entries. Replies stream: the text so far sits in the conversation's `turns` row, rewritten a few times a second and cleared in the transaction that commits the finished entry, so every process sees a reply grow by polling, as it already sees new entries. The row is also the lease that keeps one loop per conversation: a heartbeat renews it every second, so a dead process's lease runs out within 15 seconds and the next sender takes over. A message sent while a turn runs waits in `queued` and joins the journal between replies (never between a reply's tool calls and their results), and the running turn answers it. Stop sets a flag in the row, from any process; the turn notices within a fraction of a second, even while the server is silent. Stopped mid-reply, the text so far is kept as an assistant entry marked interrupted, and any half-made tool call is dropped; stopped between steps, the turn just ends. The partial reply is masked like the rest of an unrated run's thread.

**Threads.** Both front ends show one list. Every task is a thread: its latest run's conversation, or `task-<id>` with nothing said yet. Every other conversation is a chat. The core sorts the list into groups: needs you (a result to rate, a task card left open), running, open, chats, done.

**Authorship.** A task filed in a conversation the user is talking in belongs to the user, whether the model called `add_task`, the card was added, or the user typed `arity task`. The conversation is kept as the task's origin. Only a task filed from an agent's own run belongs to that run's conversation; workers cannot file tasks yet, so nothing does this.

**Task states.** As in the wiki. Ready means no blocker is open, and is recomputed after every board write. A task for an agent is assigned when its run starts, in gates once the run reports, and done when the run is rated or the user closes it without rating. Run status (running, failing, needs rating, rated) is the latest run's, shown next to the task.

**Drafting.** A task is drafted on a card attached to a chat. The card is `draft` entries in the chat's chain, so it survives restarts and forks. A model fills or changes it with `propose_task`; the person edits fields directly, and those edits reach the model as a user message. While a card is open it sits where the composer was, with a one-line message field above it, and the model's system prompt shows it. Add puts it on the board as the user's task; Dismiss closes it. The checklist button beside the composer (⌘T) attaches an empty card to the chat.

**Delegating.** Assignee `agent`, on the card, through `add_task`, or by changing it with `update_task` before work starts. The tool tells the model the user will rate the result, so it finishes its turn instead of waiting. A conversation can also do a task itself in its reply and mark it done.

**Dispatching.** `work_once` passes on one finished result or runs the most pressing ready task for an agent (priority, then due date, then age). The app calls it in a loop while open, and so does `arity work`. A claim is a lease on the trial row, taken in a write transaction, so two dispatchers never run the same task. A run whose dispatcher died is resumed from the journal once its lease runs out, or within seconds when no turn is running in its conversation and its lease has not been renewed for 15 seconds. A failed run is retried a minute later, unless its model can no longer be reached (signed out, key gone, server down): then the run is abandoned, ended without a result, never reported or scored, and the task is picked again among models that can be reached. Only reachable workers are picked. What a failure says before the run is rated is generic ("The last attempt failed; it will be tried again"); the detail names the model or its provider, so only `reveal` shows it.

**The blind pick.** Uniform among the `workers` listed in `config.json` that the task's clearance allows: `local` allows only `mlx:` workers, even if another provider is also on this computer.

**Workers.** Each run has its own conversation, `task-<id>` (`task-<id>-<n>` for a rerun), with a worker prompt and read-only board tools. Its last answer is the result. Only the latest run of a task is in the list.

**Reporting.** A finished result waits in the task's thread for the user's rating. The chat the task was filed in gets a `report` entry with the result, as plain information; it is not woken.

**Rating.** The user rates in the task's thread, where the composer would be, or with `arity rate`, and may skip. Every rating records the rater's model, empty for a person. A model never rates a run it did itself: such a run is not offered to it and `rate` refuses it. Rating a rated run replaces the rating, and `arity rate` says what it changed from.

**Fields.** The core checks a task's fields however they arrive: a due date must be a real date, tags lose repeats (ignoring case), and a title is at most 200 characters. Listings clip titles at 80. `list_tasks` leaves done tasks out unless asked with `include_done`.

**Hiding the model.** A run's model is hidden in its thread, in `runs`, and as a default model until the run is rated. Scores count rated runs only, so unrated runs cannot be traced to a model. `reveal` shows it on request.

**The rating gate.** Only for a task an agent's run filed. The report goes to that run's conversation, which is woken to rate unless its model is the one that did the work; the `rate` tool is offered only then. A conversation that ends its turn with such a result unrated gets a notice asking it to rate, up to three times since the last report. Then it is let through, and the run stays unrated for the user.

**Migration.** Opening an older database moves tasks written by a chat to the user with the chat as origin, records the rater's model on old ratings from the journal, and removes ratings a model gave its own run, so those results wait for the user.

## What is built

The journal with crash-safe resume and fork; providers in `config.json` (MLX, Nous Portal, OpenCode Zen, any OpenAI-compatible endpoint with a key) and ChatGPT through OpenAI's sign-in for apps, streamed; model lists from each provider; stopping a turn from anywhere; one writer per conversation, with messages queued for a running turn; both front ends; the wiki's task fields and states, with blockers deciding ready; task cards drafted in chat; one list of threads; delegation, the blind pick with clearance, workers, reports, rating by the user, masking, scores, reveal; the rating gate for agents; the four choices for a chat over a leaderboard of public and measured figures. Unit tests cover, on a scripted model, a streamed reply ending as one entry, a stop mid-reply that the conversation continues from, a second sender queuing instead of starting a loop, and a dead turn's lease being taken over; and also authorship, a model never rating its own run, the user's result waking no model, the rating gate, blockers deciding ready, both migrations, a card's life, provider parsing, a missing key, a key never appearing in an error, and an old ChatGPT sign-in asking for a new one; and each of the four choices against a fixed leaderboard, including private with nothing local, free with a subscription out of quota, and Arity's own ratings and speeds overtaking public figures.

## What is left

1. **Talking to a worker directly** after its run, without breaking blindness before it is rated.
2. **Papercuts.** A tool and a button to file one.
3. **Tests on a scripted model** for the full delegation loop, kill and resume included, and a check that no model name reaches the writer.
4. **Reports during a turn.** A result's note can land in a chat while a turn is running there; the turn then reads it as its next input.
5. **Requirements and gates** on tasks, once their lists are written.
6. **A real session** with two or three models, long enough to see scores separate.

## Done means

- A chat where the secretary delegates, and the result waits for the user's stars with no model woken.
- Scores show per-model averages after a few dozen runs.
- No model name appears before a rating, except through `reveal`.
- Killing the process mid-run and restarting loses nothing.
- The scripted end-to-end test passes.

## Risks

- **Small local models may call tools poorly.** The writer can be a stronger model than the workers; only worker picks are blind.
- **Ratings now depend on the user rating.** If results pile up unrated, scores stay thin.
- **Cost is zero for local models,** so scores rest on ratings and time until paid API models are added.
