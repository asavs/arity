# 1.0.1: the PRs

One entry per pull request. Each says what it is for in the project's own
words, which files it touches, what done looks like, and what it leaves alone.
The code is written by hand against these notes.

Entries are added as questions get settled. Defects that need no discussion
come first.

## Defects

### The trial's winner reaches the journal

After `arity 3 "..."`, the winner's messages are copied into the base State
but the base's session file never sees the message or the answer. The State
is no longer a fold over its journal, so a later resume loses the trial turn.
Forks are also never marked retired, so `store.unfinished()` lists every fork
ever run and `arity resume` picks one.

- `main.run_trial`: when a winner is picked, journal the Message and the
  winner's ModelCompleted into the base session, and write a record line
  naming the fork it came from. When no winner is picked, journal nothing
  and say so.
- `trial.run`: write a `retired` record into each fork's file when the fork
  finishes. A fork is not a bot; it gets no death rites and no ledger entry.
- Done when: fold the base's journal after a trial and get the same messages
  the live State has; `unfinished()` returns no forks.
- Leaves alone: the scorecard, the outcome record.

### A bot messaged mid-turn waits its turn

The loop hands a live kernel a Message whenever anyone Sends to it. If that
kernel is mid-turn (status is not IDLE), the moment appends a user message
while tool calls are outstanding and the conversation is malformed at the
provider. Reception asking the engineer, and the engineer asking reception
back, is enough to hit it.

- Policy: to be settled. See the open questions.

### Seats refresh on their clock

Nothing resets a subscription seat's `remaining` when `resets_at` passes.
`spend` subtracts output tokens per million from `remaining`, which is a
fraction for subscription seats and dollars for API seats: two units, one
field, one subtraction.

- Policy: to be settled. See the open questions.

### The archivist is a different model

`ledger.death_rites` takes an archivist seam; `Loop` defaults it to the
kernel's own model and `main` never sets one. Axiom 9 says the archivist is a
different model with a different job.

- Policy: to be settled with the staff questions.

### A CLI harness holds its session

`harness.CLIHarness` flattens the whole conversation into one prompt every
turn. `claude -p` and `codex exec` both resume a session by id, so the CLI
can hold the cached prefix and the loop can send only the newest message.
As written, a harnessed kernel is cold every turn.

- `harness.CLIHarness`: keep a session id per kernel. First call sends
  system and the first message; later calls send only the last message with
  the CLI's resume flag. Record the CLI's session id in the birth line's
  parent-style pointer so a resume can find it.
- Done when: a two-turn conversation through `claude` shows one session id
  in the CLI's own logs.
- Leaves alone: the wires, the moment.

### Cached tokens are counted

`store.usage` and `store.rows` sum tokens in and out and drop the provider's
cached-token count. Every question about the keepalive, cache breakpoints
and warm windows reads that number.

- `store.usage`, `store.rows`: add `tokens_cached`, reading
  `cache_read_input_tokens` (Anthropic) or `prompt_tokens_details.cached_tokens`
  (OpenAI-shaped).
- Done when: a row from a real two-turn session shows a nonzero cached count
  on the second turn.

## Decisions

### The bot is the file

A bot and a role are the same thing. The team is `library/bots/`, one
markdown file per bot. The filename is the name the ledger is keyed by and
the name a teammate messages. The text is what the bot is good at. The front
matter is the by-name half of a Spec: the skills and tools it carries, and a
pinned harness or effort if it has one. Cast fills in the two fields a file
cannot know, seat and model.

Two bots cannot share one aptitude text, so there is no "two engineers on
two tasks". A bot is held by one kernel at a time, like a person. Parallel
work on one task is a trial of forks. When the standings say a bot is bad at
something, a new bot with its own name is hired.

- `paths.py`, seeds: `bots.json` is gone. `library/roles/` becomes
  `library/bots/`.
- `library.py`: one small front-matter reader, used by bots and skills
  alike: `key: a, b` lines, no YAML. `bots()` lists the folder;
  `bot(name)` returns text and front matter. Each bot file carries a
  one-line `description:` that the wake text shows next to its name, so
  reception knows whom to message for what.
- `types.py`: `Spec.role` becomes `Spec.bot`. `State.bot` stays and equals
  `spec.bot`. The word "role" leaves the code; in prose it means what a bot
  is good at.
- `cast.py`: `choose(bot)` reads the front matter instead of a staff entry.
  `is_bot(name)` is "the file exists". `resolve` adds the bot's text where
  the role text went.
- `scorecard.py`, `store.rows`: keyed by bot name. `row["bot"]` and
  `row["spec"].bot` are the same string; keep one.
- `docs/outline.md`, `README.md`: the Bots entry and the reading order say
  the file is the bot.
- Done when: the smoke test passes with no `bots.json` anywhere; a new bot
  is added by writing one file and reception can message it.
- Leaves alone: the ledger, the store format, the moment.
